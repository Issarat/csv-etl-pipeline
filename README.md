# CSV ETL Pipeline

A Python ETL pipeline for three Olist e-commerce datasets: `customers`,
`orders`, and `order_items`.

The pipeline extracts source CSV files, validates and transforms each row,
writes clean and rejected CSV outputs, creates the PostgreSQL tables, and
upserts clean records into PostgreSQL.

## Project goals

- Build a repeatable ETL workflow for the core Olist order datasets.
- Keep valid records separate from rejected records so data-quality problems
  remain visible and auditable.
- Preserve identifiers, ZIP code prefixes, timestamps, and numeric values with
  database-appropriate types.
- Load related tables in dependency order while enforcing PostgreSQL keys and
  constraints.
- Support safe reruns by updating existing records instead of duplicating
  primary keys.
- Provide a local development environment that can be started consistently
  with Docker Compose.

## Features

- CSV extraction with configurable string-column handling.
- Dataset-specific validation for required fields, data types, order statuses,
  and duplicate business keys.
- Clean and rejected output files with detailed rejection reasons.
- Preservation of invalid raw date and numeric values for investigation.
- PostgreSQL schema creation from `sql/schma.sql`.
- Transactional PostgreSQL upserts with dataset-specific conflict keys.
- Foreign-key relationships between customers, orders, and order items.
- Console and file logging for pipeline and database operations.
- Source-data profiling for row counts, duplicates, memory usage, and column
  statistics.

## Data flow

```text
data/raw/*.csv
    -> extract
    -> transform and validate
    -> data/clean/*.csv
    -> PostgreSQL upsert

Invalid rows
    -> data/rejected/*.csv
```

Every rejected row contains a `rejection_reason`. Date and numeric fields that
fail conversion also retain their original values in `raw_...` columns.

## Setup

Follow the [setup guide](docs/setup.md) to create the Python environment,
configure `.env`, start PostgreSQL with Docker, and create the database schema.

## Run the ETL pipeline

After completing setup and confirming that PostgreSQL is healthy, run:

```powershell
.\.venv\Scripts\python.exe -m src.pipeline
```

For each configured dataset, the pipeline:

1. Reads the raw CSV with identifier and text columns preserved as strings.
2. Validates required fields, types, statuses, and duplicate keys.
3. Splits records into clean and rejected DataFrames.
4. Checks that clean rows plus rejected rows equal the input row count.
5. Exports clean and rejected CSV files.
6. Upserts clean rows into PostgreSQL.

Generated files use these paths:

```text
csv-etl-pipeline/
|-- compose.yaml
|-- data/
|   |-- raw/
|   |-- clean/
|   |-- rejected/
|   `-- validate/
|-- logs/
|-- sql/schma.sql
|-- src/
|   |-- configuration.py   # Dataset paths and cleaning rules
|   |-- extract.py         # CSV reading
|   |-- transform.py       # Shared cleaning and row rejection
|   |-- validate.py        # Product/category and geolocation validation
|   |-- load.py            # Lazy database setup and upserts
|   |-- pipeline.py        # Cleaning, validation, and load orchestration
|   |-- profiling.py       # Source data profiling
|   `-- logger.py          # File and console logging
|-- tests/
|-- .gitignore

```

## Profiling, logs, and tests

```powershell
.\.venv\Scripts\python.exe -m src.profiling
.\.venv\Scripts\python.exe -m pytest -q
```

Profiling reports row counts, duplicate counts, memory usage, per-column
statistics, and order-status counts. Reports are written to the console and
`logs/profiling/<dataset>.log`.

## Logs

Runtime logs are written to:

```text
logs/pipeline/<dataset>.log
logs/pipeline/main.log
logs/load/create_table.log
logs/load/<table>.log
logs/profiling/<dataset>.log
```

Exceptions are logged with their traceback and then raised so the pipeline
exits with an error instead of silently continuing.

## Tests and limitations

Run tests with:

```powershell
.\.venv\Scripts\python.exe -m pytest
```

`tests/test_transform.py` is currently empty, so automated test coverage still
needs to be implemented. The current pipeline supports only `customers`,
`orders`, and `order_items` even though other Olist source CSV files may exist
under `data/raw`.
